2-1. Microsoft 9월 정기 보안 업데이트 [긴급 · 제로데이 2건 악용 확인]
KISA 공지 #2534 | 9/9 게시
무엇이 문제인가

9/8(현지) 정기 업데이트로, KISA 집계 기준 13개 제품군에서 취약점 996개가 수정됐습니다(집계 방식에 따라 964~996건으로 보도). 월간 기준 역대 최대 규모입니다. 실제 공격에 쓰인 제로데이 2건은 둘 다 CVSS 7.8이며, 영향받는 Windows가 서로 다릅니다.

  • CVE-2026-69525 원격 데스크톱 서비스 원격 코드 실행 (9.8) — RDS·RD 게이트웨이 운영 서버
  • CVE-2026-69676 Kerberos 원격 코드 실행 (8.8, 낮은 권한 필요) — 도메인 컨트롤러
조치 방법

① PC — 설정 → Windows 업데이트 → 업데이트 확인 → 설치 후 재부팅까지 완료합니다. Office는 파일 → 계정 → 업데이트 옵션 → 지금 업데이트를 실행합니다.

해당 KB: Windows 11 24H2·25H2 KB5124008 / 23H2 KB5122880 / Windows 10 22H2·21H2(ESU 등록 PC, LTSC 2021) KB5122878

② 서버 — WSUS·SCCM·Intune에서 승인해 배포하되, 도메인 컨트롤러·DNS·RDS·Exchange 서버를 먼저 처리합니다.

③ 패치를 받을 수 없는 장비 — ESU에 등록하지 않은 Windows 10과 ESU가 없는 Server 2012/2012 R2에는 ALPC 제로데이가 그대로 남습니다. Windows 11 전환이나 ESU 등록을 우선하고, 당장 어렵다면 인터넷·내부망 접근을 제한합니다.

조치 확인 방법

PowerShell에서 현재 빌드를 확인합니다.

Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' |
  Select-Object DisplayVersion, CurrentBuild, UBR

2-2. PostgreSQL 14~18 [높음 · CVSS 최대 8.8]
KISA 공지 #2536 | 9/10 게시
무엇이 문제인가

KISA 공지의 해결 버전(14.23 / 15.18 / 16.14 / 17.10 / 18.4)은 5/14에 나온 릴리스입니다. 이 버전 미만이면 넉 달째 노출된 상태입니다. 서버와 클라이언트 취약점이 섞여 있어 둘 다 챙겨야 합니다. (CVE 번호 앞자리는 모두 CVE-2026-)

조치 방법

① 8월 최신 마이너 버전으로 바로 업그레이드 — 18.6 / 17.11 / 16.15 / 15.19 / 14.24. 18.5는 회귀 문제로 배포되지 않았습니다. 마이너 업그레이드는 데이터 변환 없이 패키지 교체와 재시작으로 끝납니다.

② 업그레이드 후 추가 조치 — 8월 릴리스 노트에 따라 GIN 인덱스가 있는 테이블의 reltuples 값을 점검해 이상하면 ANALYZE를 실행하고, btree_gist(float·bit 컬럼)나 ltree 인덱스를 쓰면 재색인합니다. 여러 버전을 건너뛰었다면 중간 릴리스 노트의 추가 조치도 확인합니다.

③ 클라이언트도 함께 — 앱 서버의 libpq, 운영자 PC의 psql·pg_dump·pg_basebackup, 컨테이너 베이스 이미지를 같은 수준으로 올립니다.

④ 바로 올리지 못하면 — 5432 포트 접근을 앱 서버로 제한(pg_hba.conf, 방화벽)하고, refint를 쓰지 않으면 제거하며, 신뢰할 수 없는 서버를 대상으로 pg_dump·pg_basebackup·pg_rewind를 실행하지 않습니다.

⑤ PostgreSQL 14는 2026-11-12 지원 종료 — 메이저 업그레이드 계획을 함께 세웁니다.

조치 확인 방법
-- 서버 버전과 마지막 기동 시각 (재시작 전에는 구버전이 계속 동작)
SELECT version();
SELECT pg_postmaster_start_time();

-- refint 사용 여부 (DB마다 실행)
SELECT extname FROM pg_extension WHERE extname = 'refint';
SELECT tgrelid::regclass AS table_name, tgname
  FROM pg_trigger t JOIN pg_proc p ON p.oid = t.tgfoid
 WHERE p.proname IN ('check_primary_key', 'check_foreign_key');
  • 클라이언트 패키지: Ubuntu/Debian dpkg -l | grep -E "libpq5|postgresql-client", RHEL 계열 rpm -qa | grep -Ei "libpq|postgresql", 도구 버전 pg_dump --version
  • 업그레이드 후 취약점 스캐너로 재점검해 해당 CVE가 더 이상 검출되지 않는지 확인합니다.

2-3. Linux 커널 [높음 · CVSS 7.8]
KISA 공지 #2537 | 9/10 게시
무엇이 문제인가

CVE-2026-31554(CVSS 7.8)는 커널 6.7에 추가된 futex_requeue 시스템콜이 서로 다른 플래그를 허용하면서 생기는 Use-After-Free입니다. 로컬 계정으로 커널 메모리를 손상시켜 권한 상승에 쓰일 수 있고, 원격 단독 공격은 불가합니다. 수정은 4월에 공개돼 주요 배포판이 이미 패치 커널을 내놓았습니다.

영향 버전: 6.7 이상이면서 6.12.80 / 6.18.21 / 6.19.11 / 7.0 미만 (각 계열의 해당 버전 이상에서 수정)

배포판 기준: Ubuntu 24.04 LTS 기본 커널(6.8 계열)이 영향을 받으며 6.8.0-136.136에서 수정됐습니다. Ubuntu 22.04 기본 커널(5.15)과 26.04는 영향이 없습니다(HWE 커널은 별도 확인). 업스트림 기준 6.7 미만 커널에는 해당 코드가 없지만, 백포트가 많은 배포판은 벤더 공지로 확인하세요. RHEL 10은 6.12 계열입니다.

함께 확인: GhostLock (CVE-2026-43499) — 같은 futex 영역의 로컬 권한 상승 취약점으로 7/7 공개됐고 공개 PoC가 있습니다. 2.6.39부터 7.0까지 대부분의 커널(RHEL 8·9·10 포함)에 영향을 주며 컨테이너 탈출도 가능합니다. KISA 이번 공지 대상은 아니지만, '6.7 미만이라 해당 없음'으로 커널 업데이트를 건너뛰지 마세요.
조치 방법

① 배포판 최신 커널 설치 후 재부팅 — Ubuntu sudo apt update && sudo apt full-upgrade, RHEL 계열 sudo dnf update kernel

② 재부팅이 어렵다면 — 배포판 라이브패치(Ubuntu Livepatch, RHEL kpatch) 적용 여부를 확인합니다.

③ 컨테이너 환경 — 컨테이너는 호스트 커널을 공유하므로 노드(호스트) 커널을 업데이트합니다. 여러 사용자가 접속하는 서버와 컨테이너 호스트를 먼저 처리합니다.

조치 확인 방법
  • uname -r → 실제 동작 중인 커널을 확인합니다. 설치만 하고 재부팅하지 않으면 구버전이 계속 동작합니다. Ubuntu 24.04는 6.8.0-136 이상인지 봅니다.
  • Ubuntu: pro fix CVE-2026-31554, pro fix CVE-2026-43499 → 해결 상태가 표시됩니다.
  • RHEL 계열: dnf updateinfo list --cve CVE-2026-43499 → 목록이 비어 있으면 이미 적용됐거나 해당 없음입니다(--installed 옵션으로 적용 이력 확인).
  • 자체 빌드 커널: 수정 커밋 포함 여부를 확인합니다(예: 6.12 계열 027145ace09f).

2-4. Adobe Commerce · Magento Open Source (운영 시 해당) [긴급 · 인증 없는 원격 코드 실행 · 악용 확인]
KISA 공지 #2535 | 9/9 게시
무엇이 문제인가

CVE-2026-75650(CVSS 10.0, 별칭 StyleSmuggler)은 템플릿 엔진의 특수문자 처리 오류로 인증 없이 원격 코드 실행이 가능한 제로데이입니다. 보안업체 관측 기준 9/4부터 공격이 있었고, Adobe가 9/7 긴급 공지(APSB26-146)와 핫픽스 VULN-39341을 배포했으며 CISA가 9/8 KEV에 등재했습니다. 공격자가 웹셸과 백도어를 심은 사례가 보고됐습니다.

버전 번호로는 판단할 수 없습니다. 2026년 8월 릴리스(-2026-aug)까지 영향 대상입니다. 9/8 정기 보안 릴리스(APSB26-138)를 적용한 곳도 핫픽스 적용 여부를 따로 확인하세요.

영향 버전: Adobe Commerce 2.4.4~2.4.9, Commerce B2B 1.3.3~1.5.3, Magento Open Source 2.4.6~2.4.9 (각 -2026-aug 이하)

조치 방법

① 버전에 맞는 VULN-39341 핫픽스 적용 — Adobe KB의 버전별 표에서 해당 패치 파일(zip)을 내려받아 'Adobe 제공 composer 패치 적용' 절차대로 적용합니다. 최근 릴리스(-2026-aug, -2026-jul 등)는 공통 패치를, 그보다 오래된 버전은 전용 패치 파일을 씁니다.

② 자격증명 전면 교체 — Adobe는 암호화 키만 바꿔서는 부족하다고 안내합니다. 유지보수 모드와 cron을 멈춘 뒤 암호화 키, 관리자 비밀번호, REST/SOAP/GraphQL 통합 토큰, OAuth 시크릿, 결제 게이트웨이 API 자격증명(결제사 측에서), DB·SSH·배포 키, 배송·세금 등 외부 연동 API 키를 교체하고, 캐시를 비운 다음 서비스를 재개합니다.

③ 침해 점검 — 9/4 이후 운영된 서버는 웹셸과 백도어 설치 여부를 확인합니다.

조치 확인 방법
  • vendor/bin/magento-patches -n status | grep "39341\|Status" → 상태가 Applied인지 확인합니다(Quality Patches Tool 설치 필요).
  • find pub/media pub/static -name "*.php*" → 결과가 나오면 즉시 조사합니다. pub/ 최상위 PHP 파일이 기본 구성(index.php, get.php, static.php, cron.php, health_check.php)과 다른지도 봅니다.
  • 관리자 사용자와 통합(Integrations) 목록에 모르는 항목이 없는지, 서버에 낯선 상주 프로세스나 cron 항목이 없는지 확인합니다.

2-5. Fortinet FortiOS · FortiSwitchManager [긴급 추가 · 인증 없는 원격 코드 실행 · 악용 확인]
KISA 공지 #2539 | 9/14 게시 (긴급 추가)
무엇이 문제인가

무선 컨트롤러 데몬(cw_acd)이 CAPWAP 제어 패킷을 처리할 때 힙 오버플로가 발생해, 인증 없이 외부에서 장비에 코드를 실행할 수 있습니다(CVE-2025-25249). CVSS는 NVD 9.8, Fortinet 자체 평가 7.4입니다.

Fortinet은 2026년 1월에 이미 패치를 배포했지만, 9/9 CISA가 실제 공격을 확인해 KEV에 등재했습니다. 1월 이후 업그레이드하지 않은 장비는 약 8개월간 노출돼 있었던 셈입니다. CISA는 FortiSASE도 영향 제품에 포함했습니다.

영향 버전: FortiOS 6.4 전체, 7.0.0~7.0.17, 7.2.0~7.2.11, 7.4.0~7.4.8, 7.6.0~7.6.3 / FortiSwitchManager 7.0.0~7.0.5, 7.2.0~7.2.6

조치 방법

① 펌웨어 업그레이드 — FortiOS 7.0.18 / 7.2.12 / 7.4.9 / 7.6.4 이상, FortiSwitchManager 7.0.6 / 7.2.7 이상. FortiOS 6.4는 KISA 권고대로 지원 중인 상위 버전으로 이전합니다. 작업 전에 Fortinet 업그레이드 경로와 HA 구성 호환성을 확인합니다.

② 바로 올릴 수 없다면 (Fortinet 우회책) — Security Fabric이 필요 없는 인터페이스에서 fabric 접근을 뺍니다. set allowaccess는 목록 전체를 덮어쓰므로 기존에 허용하던 서비스를 모두 다시 적어야 합니다.

config system interface
    edit "wan1"
        set allowaccess ping https ssh    # fabric 제외, 기존 허용 서비스는 유지
    next
end

Fabric을 유지해야 하면 local-in 정책으로 CAPWAP 제어 트래픽(UDP 5246~5249)을 신뢰 장비 IP에서만 허용합니다.

③ 침해 점검 병행 — 이미 악용 중인 취약점이므로 패치와 별도로 모르는 관리자 계정, 설정 변경 이력, 낯선 VPN 세션이나 외부 연결이 없는지 확인합니다.

조치 확인 방법
  • get system status → Version이 위 해결 버전 이상인지 확인합니다. HA 구성이면 양쪽 노드 모두 확인합니다.
  • show system interface | grep -f fabric → 외부 인터페이스에 fabric이 남아 있지 않은지 확인합니다.
  • 우회책을 쓴 경우 show firewall local-in-policy로 CAPWAP 허용 대상이 신뢰 IP뿐인지 보고, 외부에서 UDP 5246 응답이 없는지 점검합니다.
  • show system admin으로 모르는 관리자 계정이 없는지, 이벤트 로그에서 설정 변경과 관리자 로그인 기록을 확인합니다.

2-6. GitLab CE/EE (자체 설치형) [긴급 추가 · CVSS 10.0 · 악용 확인]
KISA 공지 #2538 | 9/14 게시 (긴급 추가)
무엇이 문제인가

GitLab이 9/10 긴급 패치(19.3.2 / 19.2.6 / 19.1.8)로 보안 취약점 18건을 고쳤습니다. 핵심인 CVE-2026-85706(CVSS 10.0)은 저장소 commits API의 경로 제한과 인증 확인이 빠져 로그인 없이 서버의 임의 파일(설정 파일, 시크릿 등)을 읽을 수 있는 문제입니다. GitLab은 이 취약점이 CISA KEV에 추가됐다고 공지했습니다. GitLab.com과 Dedicated는 조치가 끝났고 자체 설치형만 해당합니다.

함께 수정된 고위험 건(EE 전용): CVE-2026-87719(9.9)는 Duo Chat 권한이 있는 로그인 사용자가 GraphQL 구독 인자를 조작해 Advanced Search 설정과 민감 자격증명을 얻을 수 있고, CVE-2026-88765(8.5)는 조작한 프로젝트 가져오기로 원격 코드 실행이 가능합니다.

영향 버전(CVE-2026-85706): 18.7 이상 19.1.8 미만, 19.2 이상 19.2.6 미만, 19.3 이상 19.3.2 미만. 나머지 17건은 더 오래된 버전까지 걸쳐 있으므로 18.7 미만이라도 최신 패치 버전으로 올려야 합니다.

조치 방법

① 즉시 업그레이드 — 19.3.2 / 19.2.6 / 19.1.8 이상. Omnibus(Ubuntu) 예:

sudo apt-get update
sudo apt-get install gitlab-ee=19.3.2-ee.0    # CE는 gitlab-ce=19.3.2-ce.0

이번 패치에는 DB 마이그레이션이 있어 단일 노드는 업그레이드 중 서비스가 멈춥니다. 작업 시간을 확보하고, 다중 노드는 무중단 업그레이드 절차를 따릅니다. 오래된 버전에서 올릴 때는 GitLab 업그레이드 경로 도구로 필수 경유 버전을 먼저 확인합니다.

② 업그레이드 전 임시 완화 — 인터넷에 노출된 인스턴스는 방화벽이나 리버스 프록시에서 접근을 사내망·VPN으로 제한합니다. 벤더가 제시한 공식 우회책은 아닙니다.

③ 시크릿 교체 검토 — 파일 읽기가 이미 시도됐을 수 있으므로 /etc/gitlab/gitlab-secrets.json, gitlab.rb에 적힌 비밀번호, DB 자격증명, 러너 등록 토큰, 외부 연동 토큰의 교체를 검토합니다.

조치 확인 방법
  • sudo gitlab-rake gitlab:env:info 또는 관리자 영역(/admin)에서 버전을 확인합니다. API로는 curl -H "PRIVATE-TOKEN: <토큰>" https://<GitLab주소>/api/v4/version
  • 악용 시도 점검: GitLab이 공개한 탐지 규칙 3종(gitlab.yml 읽기 시도, metadata.path 파라미터를 이용한 파일 읽기, 파일 경로 열거)을 기준으로 접근 로그를 봅니다.
sudo zgrep -h "repository/commits" /var/log/gitlab/nginx/gitlab_access.log* \
  | grep -Ei "metadata|%2e%2e|\.\./"

패치 전 기간에 이런 요청이 200 응답으로 남아 있으면 침해를 전제로 시크릿 교체와 추가 조사를 진행합니다.
